applyVocabularyCorrections(rawText: string, rules: VocabularyRule[]) { let correctedText = rawText; const appliedRules = []; // Sort by length (longest first to avoid conflicts) const sortedRules = rules .filter(r => r.isActive) .sort((a, b) => b.incorrectTerm.length - a.incorrectTerm.length); for (const rule of sortedRules) { // Word-boundary regex matching const regex = new RegExp(`\\b\${rule.incorrectTerm}\\b`, 'gi'); const matches = correctedText.match(regex); if (matches) { correctedText = correctedText.replace(regex, rule.correctTerm); appliedRules.push({ originalTerm: rule.incorrectTerm, correctedTerm: rule.correctTerm }); } } return { correctedText, appliedRules }; }

🔬 Detailed Sub-Features Explanation

🔍 Searchable Library - Sub-Features

1. Full-Text Search with Typo Tolerance

Implements fuzzy search using Meilisearch's built-in typo tolerance. Handles misspellings, partial matches, and phonetic variations automatically.

Implementation:

Uses Meilisearch's `typoTolerance` configuration with ranking rules. Falls back to local stemming and Levenshtein distance when Meilisearch is unavailable.

2. Semantic Search Using Vector Embeddings

Converts text to vector embeddings using AI models, then performs cosine similarity search to find conceptually similar content beyond exact keyword matches.

Implementation:

Uses pgvector for PostgreSQL vector storage. Embeddings generated via AI Services endpoint. Falls back to concept-based keyword mapping when vector search unavailable.

3. Hybrid Result Blending

Combines results from text search and semantic search using configurable weights (default 0.5/0.5) to provide the most relevant results.

Implementation:

Algorithm: `finalScore = (textScore * textWeight) + (semanticScore * semanticWeight)`. Deduplicates by entity ID, keeps best snippet from either source.

4. Fuzzy Matching with Stemming

Applies linguistic stemming to reduce words to their root form (e.g., "pricing" → "price") for broader matching capabilities.

Implementation:

Custom stemming function for English. Combined with Levenshtein distance for edit-distance-based matching when exact matches fail.

5. Advanced Filtering

Multi-dimensional filtering including sentiment (Positive/Negative/Neutral), topic tags, agent name, channel type (call/email), and date ranges with presets.

Implementation:

Filter pipeline applies filters sequentially. Date presets (Today, This week, This month, etc.) converted to actual date ranges before query execution.

6. Snippet Generation

Extracts relevant context around matched terms to provide users with preview snippets showing why a result matched their query.

Implementation:

Extracts 40 characters before and 60 characters after match point. Truncates at word boundaries for readability.

7. Multi-Tenant RLS Policies

Row-Level Security ensures all search results are automatically scoped to the requesting tenant's data, preventing cross-tenant data leakage.

Implementation:

PostgreSQL RLS policies use `app.current_tenant_id` session parameter. All queries include tenant_id in WHERE clause for additional safety.

🏷️ AI Topic Tagger - Sub-Features

1. Multi-Provider AI Fallback

Three-tier fallback strategy: Groq (Llama-3.3) → Gemini-2.0 → Keyword-based matching ensures topic tagging works even if primary AI providers fail.

Implementation:

Sequential API calls with try-catch blocks. Each provider uses same prompt structure for consistency. Keyword fallback uses predefined mapping.

2. Confidence Scoring

Each detected topic assigned a confidence score (0.0-1.0) indicating AI's certainty. Only topics above threshold (default 0.70) are stored.

Implementation:

AI returns confidence in response. Normalized to 0-1 range. Filtered by threshold before database storage to ensure quality.

3. Evidence Snippet Extraction

Extracts direct quotes from transcript (max 100 chars) that support the topic detection, providing transparency and audit trail.

Implementation:

AI instructed to find supporting quotes. Stored in `evidence_snippet` field. Displayed in UI to show why topic was tagged.

4. Topic Explanation Generation

AI generates 1-2 sentence explanations for why each topic was detected, helping users understand the classification logic.

Implementation:

Part of AI prompt response. Stored in `explanation` field. Provides context for manual review and quality assurance.

5. Custom Topic Taxonomies

Tenants can define custom topic models with their own taxonomies, descriptions, and categorization (global vs tenant-specific).

Implementation:

Stored as JSONB in `m02_topic_models.topics`. Each topic has name and optional description. Type field distinguishes global from custom.

6. Deduplication and Threshold Filtering

Removes duplicate topic assignments and filters out low-confidence detections to maintain quality of topic tags.

Implementation:

Case-insensitive deduplication using Set. Sorted by confidence before filtering. Configurable threshold (default 0.70) allows tuning.

7. Version Tracking

Topic models track when they were last trained/updated, enabling audit trail and version management of taxonomies.

Implementation:

`last_trained_at` timestamp in topic models. Updated on any taxonomy change. Allows rollback to previous versions if needed.

🌐 AI Translator - Sub-Features

1. AI-Powered Translation

Uses Groq Llama-3.1-8b-instant model for high-quality translations across multiple languages with context awareness.

Implementation:

Direct API call to Groq chat completions. Temperature 0.3 for consistent output. Prompt engineered to return only translated text.

2. Database-Based Caching

All translations cached in `m02_translated_texts` table to avoid redundant API calls for the same content.

Implementation:

Cache key: tenantId + entityType + entityId + targetLanguage. Cache checked before API call. Results stored after successful translation.

3. Workspace Language Settings

Tenant-specific configuration for default language, fallback language, and supported languages for automatic translation.

Implementation:

Stored in `m02_workspace_language_settings`. Auto-created with defaults if not exists. Used by search and detail views.

4. Bulk Translation Support

Efficiently translates arrays of text in a single API call, reducing overhead for multiple items (e.g., diarized transcripts).

Implementation:

Single API call with JSON array prompt. Validates array length matches input. Temperature 0.1 for precise array formatting.

5. Fallback Mechanism

When AI translation fails, returns mock translation with language prefix (e.g., "[ES] original text") to ensure system continues functioning.

Implementation:

Try-catch around API call. On error, returns `[LANG] original_text` format. Sets `fallback: true` flag for bulk operations.

6. Quality Status Tracking

Tracks translation quality status (success/failure) to monitor AI performance and identify problematic translations.

Implementation:

`quality_status` field in cache table. Currently set to 'success' on successful translation. Can be extended with scoring.

7. Multi-Entity Support

Translates different entity types: summaries, coaching suggestions, search titles, search snippets, and full transcripts.

Implementation:

`entity_type` field in cache table distinguishes content types. Different caching strategies per entity type if needed.

📝 AI Transcriber - Sub-Features

1. Custom Vocabulary Rules

Users can define custom incorrect→correct term mappings to fix common transcription errors specific to their domain.

Implementation:

Stored in `m02_vocabulary_corrections`. Each rule has incorrect_term, correct_term, category, language. Tenant-scoped for isolation.

2. Mispronunciation Support

Supports mapping of common mispronunciations to correct terms, capturing variations like "sales-forse" → "Salesforce".

Implementation:

`mispronunciations` TEXT[] field stores array of mispronunciations. Can be extended to match these in addition to main term.

3. Term Variations

Supports alternative spellings and variations of terms to handle different transcription styles and accents.

Implementation:

`variations` TEXT[] field stores alternative spellings. Currently stored for future use in matching logic.

4. Language-Specific Rules

Vocabulary rules can be language-specific, allowing different correction sets for different languages (e.g., English vs Spanish).

Implementation:

`language` field (default 'en'). Rules filtered by language when applying corrections. Enables multi-language support.

5. Version Tracking

Tracks correction version for each transcript, enabling audit trail and rollback to previous versions if needed.

Implementation:

`correction_version` field in calls/emails tables. Increments on each correction. Starts at 0 (uncorrected).

6. Correction History Logging

Every correction applied is logged in `m02_transcript_corrections` table with original term, corrected term, and timestamp.

Implementation:

Each replacement creates a record. Enables analytics on most common corrections and audit trail for compliance.

7. Statistics Dashboard

Provides metrics on vocabulary correction usage: total rules, corrections this month, and percentage of enhanced transcripts.

Implementation:

Aggregates from vocabulary_corrections and transcript_corrections tables. Calculates enhancement percentage from correction_version > 0.
